在前几篇关于 MCU 项目架构的文章基础上，结合后续的设计与实践，本文进一步梳理和优化目录职责、模块依赖与任务流

这次调整重点明确三个问题：产品如何组织任务，组件如何提供能力，以及平台如何适配硬件

本文以 `bus_motor` 总线电机 SDK 为设备案例，结合一个机械臂关节控制场景，说明产品层如何使用设备能力，以及各部分如何协作

## 一、为什么需要重新划分职责

一个 MCU 项目刚开始时，代码通常比较直接：初始化外设，在循环中读取输入，再控制电机或其他执行机构

随着功能增加，代码会逐渐承担不同职责：

- 产品任务需要决定机械臂运动到哪里
- 设备接口需要发送电机位置命令、读取电机反馈
- 厂家驱动需要处理协议和 CAN 帧
- 平台代码需要调用具体 MCU 的 CAN 驱动
- 任务编排需要决定各项任务何时执行、数据如何传递

这些职责需要各自清晰的归属，让修改产品动作、更换电机和适配平台时，都能找到对应的代码边界

## 二、整体目录：产品、组件与平台

先看整体结构：

```text
src/
├── product/
│   ├── app/
│   ├── assemble/
│   ├── service/
│   └── domain/
├── components/
│   ├── device/
│   ├── domain/
│   └── infra/
└── platform/
```

各部分职责如下：

| 目录 | 职责 |
| --- | --- |
| `product/app` | 编排产品任务，决定调用时机、跨服务数据流和跨任务操作顺序 |
| `product/assemble` | 选择具体实现，确定实例与共享关系，提供资源、绑定依赖并组织初始化 |
| `product/service` | 实现产品中的具体任务，维护任务状态并执行外部操作 |
| `product/domain` | 表达当前产品独有的概念、规则、判定和状态转换 |
| `components/device` | 提供可复用的设备族接口、具体驱动和协议实现 |
| `components/domain` | 提供可独立于产品、设备和平台运行的通用算法 |
| `components/infra` | 提供具有明确职责的基础能力，例如时间运算和日志接口 |
| `platform` | 适配目标 MCU、SDK、板卡和运行环境，实现组件所需的契约 |

对于机械臂关节控制，可以这样理解：

```text
product/app
    安排输入采集、目标生成与关节控制的执行顺序

product/assemble
    选择 J1 关节使用的具体电机并完成绑定

product/service
    执行关节控制任务，调用电机接口

product/domain
    表达当前机械臂产品的运行模式与动作规则

components/device
    提供 bus_motor 统一接口与具体电机驱动

platform
    提供 CAN 发送、时间等底层适配
```

这里展示的是调整后的职责划分，现有 `bus_motor` SDK 可以作为其中设备部分的案例

目录按项目实际需要创建：规模较小时，`assemble` 可以使用与 `app`、`service` 同级的单个 `assemble.c`；简单的产品规则也可以先放在所属服务旁边，等职责值得独立时再拆分

## 三、装配负责组成，模块负责初始化

产品启动时，需要决定使用哪些模块、创建多少实例，以及各部分之间如何连接

这些产品层面的选择由 `assemble` 负责

例如，机械臂 J1 关节使用一台达妙电机时，装配部分需要确定：

- J1 对应的逻辑电机 ID
- 实际使用的电机型号、CAN ID 和固件版本
- 电机驱动需要的底层端口
- 按实际数量提供的电机实例存储
- 各模块的初始化与绑定顺序

在 `bus_motor` 中，业务侧可以定义逻辑电机 ID：

```c
typedef enum {
    MOTOR_ARM_J1 = 0,
    MOTOR_ARM_J2,
} RobotMotorId;
```

`MOTOR_ARM_J1` 表示产品中的 J1 关节，具体硬件信息由装配时的配置表达，例如：

```c
static const DmMotorConfig s_j1_config = {
    .can_id = 0x01u,
    .master_id = 0x11u,
    .model = DM_MOTOR_MODEL_DM4340,
    .firmware = {
        .major = DM_MOTOR_FIRMWARE_V4,
    },
    .default_mode = DM_MOTOR_MODE_POS_VEL,
};
```

随后，装配代码提供实例存储，调用 `bus_motor.init()`、`dm_motor_init()` 和 `dm_motor_bind()`，建立逻辑 ID 与具体电机实例之间的关系

```text
MOTOR_ARM_J1
      ↓
assemble 绑定
      ↓
达妙电机实例
      ↓
型号、固件版本、CAN ID 等具体配置
```

`assemble` 决定使用哪个实现并提供资源；实例内部状态如何建立，由设备模块自己的初始化与绑定入口负责

如果多个模块共享同一个资源，初始化时机由掌握整体使用关系的一方决定；模块内部固定使用的依赖，可以由模块直接使用

**装配决定系统如何组成，模块决定自己如何初始化**

## 四、服务负责执行，`app` 负责编排

在一个机械臂产品中，可以有输入采集服务、目标生成服务和关节控制服务

下面是一种可能的任务流：

```text
输入采集服务发布输入结果
            ↓
app 取得输入并传递给目标生成服务
            ↓
目标生成服务结合产品规则生成目标
            ↓
app 将目标传递给关节控制服务
            ↓
关节控制服务通过 bus_motor 发送命令
            ↓
根据操作结果和电机反馈更新任务状态
```

实际项目可以根据产品功能调整服务名称和拆分方式

跨服务数据流由 `app` 显式组织：生产方发布结果，`app` 将消费者所需的数据作为输入传入，让数据来源和传递时机都能直接看到

### 服务由外部驱动

服务说明自己的运行要求，例如调用时机、是否阻塞、允许在哪种执行上下文中运行；`app` 根据当前产品决定怎样满足这些要求

裸机项目可以在主循环中按时间和事件调用服务；RTOS 项目可以将任务流放进任务或其他合适的调度结构

两种情况下，服务的职责可以保持一致，变化的是产品如何安排它们

服务按自身职责设计入口：有的服务需要初始化和周期处理，有的只需要在收到输入时执行一次操作

### 跨服务数据需要明确有效范围

对于目标位置这样的小值，可以直接按值传递

如果一次发布的数据较大，可以使用只读视图，避免不必要的复制；此时需要说明视图对应哪一次发布，以及消费者在什么时间范围内可以使用它

数据的更新时机和跨任务访问方式，也需要结合实际调度方式明确下来

### 服务状态按实例需求组织

单实例服务可以在自己的 `.c` 文件中使用私有 `static` 保存状态

需要多个实例，或者需要隔离不同运行上下文时，再使用显式实例；服务状态由需要持有它的一方管理

## 五、通用算法与产品规则分开表达

机械臂控制中可能同时出现两类逻辑：一类是对输入进行滤波或轨迹计算，另一类是根据当前产品模式决定关节应该执行什么动作

它们都涉及计算，但职责不同

### 通用算法：明确输入、输出与下一状态

如果一个滤波或轨迹计算算法不依赖当前产品、具体设备和平台，可以放在 `components/domain`

这类算法采用明确的输入输出边界：

- 输入数据、配置和旧状态只读
- 需要时间信息时，由调用方显式传入
- 结果可以按值返回，也可以写入调用方指定的输出
- 需要跨轮运行时，由调用方提供旧状态，算法输出下一状态
- 输出空间与输入、旧状态使用不同的内存
- 算法内部不执行外部 I/O，也不修改其他外部状态

例如，轨迹计算可以接收当前目标、配置和旧状态，输出本轮结果与下一状态；调用方决定何时采用下一状态

这种边界让算法能够脱离电机和具体产品单独运行，也让每一轮计算的输入与结果更容易被检查

### 产品规则：描述当前产品如何判断

“当前模式下，机械臂应当进入哪个动作阶段”“收到某种输入后应该生成什么动作意图”，属于产品自身的规则，可以放在 `product/domain`

产品领域可以读取固定的产品规则，也可以更新显式传入的领域实例，状态修改范围限于该实例自身；当前时间、运行配置、其他模块的结果等外部可变事实，由调用方提供

产品领域可以使用通用算法，也可以输出简单的动作意图，例如“将 J1 移动到目标位置”

**动作意图表示产品规则要求做什么，实际动作是否完成由执行结果确定**

关节控制服务通过 `bus_motor` 发送目标位置后，可以结合电机反馈和产品定义的完成条件判断是否到位

## 六、用 `bus_motor` 看设备接口与平台适配

`bus_motor` 的主要结构如下：

```text
bus_motor/
├── bus_motor.h
├── bus_motor.c
├── dm_motor.h
├── dm_motor.c
├── dji_motor.h
├── dji_motor.c
└── dm_motor/
    ├── dm_motor_core.h
    ├── dm_motor_core.c
    ├── dm_motor_protocol.h
    ├── dm_motor_protocol_v3.c
    └── dm_motor_protocol_v4.c
```

其中，`bus_motor.h/.c` 提供总线电机的公共接口和统一分发；`dm_motor` 提供达妙电机的配置、绑定和厂家适配；达妙不同版本的协议细节放在对应的协议实现中

它与本文的设备职责可以对应为：

```text
产品服务
   ↓
BusMotorInterface
   ↓
BusMotorDriver 与具体电机实例
   ↓
厂家驱动和协议实现
   ↓
BusMotorPortOps
   ↓
平台提供 CAN、时间等能力
```

### 设备族向上提供公共接口

`bus_motor` 对上提供电机控制语义，例如位置、速度、扭矩和阻抗控制

业务层可以通过逻辑电机 ID 发送位置目标：

```c
bus_motor.pos(MOTOR_ARM_J1, target_position);
```

也可以读取位置反馈：

```c
float position;

if(bus_motor.feedback.position(MOTOR_ARM_J1, &position) == MOTOR_STATUS_OK) {
    // 使用位置反馈
}
```

在这个接口中，位置单位为 `rad`

业务层通过 `MOTOR_ARM_J1` 表达“操作哪个产品关节”，具体的 CAN ID、厂家协议帧和固件版本由设备相关代码处理

统一入口表达的是**上层依赖的公共控制语义**，各厂家是否支持某项能力，由具体实现和实例能力决定

### Profile 表达公共控制语义

`bus_motor` 使用 Profile 表示当前采用的厂家无关控制语义，例如位置、速度或阻抗控制

以达妙电机为例，公共 Profile 需要映射到厂家实际支持的硬件模式；同一个厂家模式也可能承载不同的公共控制语义

```text
公共 Profile
    产品希望采用什么控制语义

厂家模式
    具体设备如何实现该控制语义
```

初始化阶段，可以使用 `bus_motor.profile.require()` 检查当前业务所需能力，并通过 `bus_motor.profile.activate()` 激活所需 Profile

达妙配置中的 `default_mode` 表示绑定时认定的初始硬件模式，公共 Profile 需要通过相应流程激活；实际接入时还需要保证 CAN 接收回调能够工作

### 设备定义向下需要的端口

达妙驱动通过 `BusMotorPortOps` 使用底层能力，例如发送 CAN 帧和获取时间

平台提供这些操作的具体实现，装配时再绑定给电机驱动：

```text
达妙电机驱动
      ↓
BusMotorPortOps
      ↓
当前平台的 CAN 和时间实现
```

设备侧表达自己需要什么，平台负责适配这些需求；设备代码及其端口契约可以脱离具体平台头文件独立编译

当前达妙接入流程中的模式切换需要等待应答，SDK 对接收回调和相关端口有相应要求，这些运行契约需要在集成时一并满足

### 实例与后端按需求选择

`bus_motor` 通过逻辑 ID、注册关系和厂家驱动表连接不同实例，这些机制服务于它统一管理多个电机的需求

其他设备可以按实际情况选择显式实例、句柄或逻辑 ID，注册表、能力查询和组操作也分别按需求引入

后端可以在构建时选定，也可以在初始化时绑定；默认在实例生命周期内保持固定，产品明确要求在线切换后端时，再定义在途操作、回调归属和状态交接规则

**切换后端**与 `bus_motor` 运行时切换 Profile 是两件事：前者改变实例使用的具体实现，后者改变电机当前采用的控制语义

## 七、操作结果与任务连续性

模块需要如实表达本次操作的实际结果

简单操作可以使用普通返回值；当调用者需要区分多种结果时，再定义模块自己的状态类型

`bus_motor` 使用 `BusMotorStatus` 表达操作结果，调用者可以据此区分操作成功、能力不支持等情况，再由产品任务规则决定后续行为

例如，发送位置命令之后，关节控制服务需要区分：

- 命令调用返回了什么结果
- 当前是否取得了所需的电机反馈
- 产品定义的到位条件是否已经满足

这三个结果分别描述命令执行、反馈获取和产品动作完成情况

当单项操作没有完成时，应如实反馈结果，并继续推进仍具备执行条件的工作；某一步确实无法进行，就说明具体阻塞点，其他任务是否继续，由实际条件和已确认规则决定

对于潜在安全隐患，说明具体触发条件和可能影响，由产品负责人决定是否引入安全机制以及如何实现；任务流按照已确认的产品规则运行

已有产品规则足以决定的事项，直接按规则处理；尚未确认的设计取舍如果会实质改变依赖、行为或协作方式，再说明差异并交由产品负责人决定

## 八、把公共契约写在接口旁边

一个接口即使只有几个参数，也需要说明使用条件：位置使用什么单位，返回值代表什么，输出数据由谁持有，函数是否阻塞，可以在哪种上下文调用

这些信息属于公共契约，应当写在 `.h` 中对应声明的旁边，并使用 Doxygen 组织：

- 普通函数的约定写在函数声明旁
- `Interface` 和 `PortOps` 的回调约定写在对应成员旁
- 单位、返回值、完成条件、所有权、寿命和调用上下文等内容，根据实际接口按需说明
- `.c` 中的注释主要用于解释实现原因

例如，`bus_motor` 的位置接口说明位置单位为 `rad`；对于需要等待应答的操作，还需要让调用者知道它的阻塞行为和运行条件

接口名称说明“可以做什么”，接口契约进一步说明“调用者应当怎样使用，以及可以依据结果作出什么判断”

## 九、X-Macro 和文件模板

### X-Macro 与接口设计独立决定

X-Macro 适合一组稳定条目需要派生多种表示的场景，例如同一份状态条目需要生成枚举和名称映射

如果一张普通 `static const` 表已经能够做到只维护一次，就使用普通表；各个条目的具体行为留在普通函数中

是否使用 X-Macro，取决于同一组数据需要如何维护和派生，与是否设计 `Interface` 是两个独立问题

### 文件模板用于保持结构一致

C 文件可以使用固定的基础分区，让变量、私有函数声明、对外函数实现和私有函数实现有稳定的位置：

```c
// ! ========================= 变 量 声 明 ========================= ! //

// ! ========================= 私 有 函 数 声 明 ========================= ! //

// ! ========================= 接 口 函 数 实 现 ========================= ! //

// ! ========================= 私 有 函 数 实 现 ========================= ! //
```

当该文件定义了对外导出的接口对象时，在私有函数声明之后、接口函数实现之前增加「接口变量定义」区

模板保持文件结构一致，模块之间的职责、依赖和契约则结合实际功能设计

## 十、让职责与选择留在合适的位置

回到机械臂关节控制的例子，整个系统可以分成几件明确的事：

- `assemble` 选择 J1 使用的具体电机，提供资源并完成绑定
- `app` 安排产品任务的调用时机和数据流
- `service` 执行关节控制任务，调用设备接口并处理结果
- `product/domain` 表达产品模式和动作规则
- `components/domain` 提供可以独立运行的通用算法
- `bus_motor` 定义公共控制语义，并连接具体厂家实现
- `platform` 提供当前 MCU 和板卡所需的底层适配

这种划分让产品在调整任务流程、修改产品规则或更换设备时，可以沿着明确的职责边界判断哪些部分需要变化

目录、接口和模板共同表达这些边界，核心始终是：**每个模块负责什么、依赖从哪里来，以及数据和执行结果如何在任务之间流动**
